做玩具，是检验设计直觉最快的方式

一个玩具没有需求文档、没有老板、也没有借口。它会在五分钟内告诉你，你的手感到底行不行。

工作里的项目太慢了。一个按钮的手感要等三轮评审、两次排期、一次灰度，等你终于摸到它的时候，已经忘了当初为什么这么设计。玩具不一样：从想法到能上手玩，中间只有一个下午。

我在工具实验室里放了三个东西。它们都很小，但每一个都逼我回答了一个真问题。

涂鸦板：延迟感是怎么来的

第一个版本，我从 pointermove 事件里拿坐标直接画点。结果线看起来是断的——因为指针事件的采样率跟不上手的移动速度，快速划过的轨迹上会出现一串离散的点。

修法是把"点"改成"线"：记住上一个坐标，每来一个新坐标就画一段 lineTo，并设置 lineCap: round 和 lineJoin: round 让接头平滑。

function stroke(a, b) {
  ctx.strokeStyle = color;
  ctx.lineWidth = size;
  ctx.lineCap = "round";
  ctx.lineJoin = "round";
  ctx.beginPath();
  ctx.moveTo(a.x, a.y);
  ctx.lineTo(b.x, b.y);
  ctx.stroke();
}

还有一个隐蔽的坑：canvas 有内部像素尺寸和 CSS 显示尺寸两套坐标。用 e.clientX 直接当绘制坐标，只在画布 1:1 显示时才对。正确做法是先按 getBoundingClientRect() 换算：

const r = canvas.getBoundingClientRect();
const x = (e.clientX - r.left) / r.width  * canvas.width;
const y = (e.clientY - r.top)  / r.height * canvas.height;

这样画布可以随意响应式缩放，笔迹都落在该落的地方。这个换算我后来在贪吃蛇和生命游戏里又抄了两遍——它值得成为肌肉记忆。

贪吃蛇：一次关于"节奏"的教训

我第一版用 setInterval 推进游戏。问题在移动端立刻暴露：切换标签页回来，游戏会瞬间补跑十几步，蛇直接撞墙。用户看到的是"我一回来就死了"，体验极差。

换成 requestAnimationFrame 加时间累加器之后，逻辑步进和渲染帧率解耦，卡顿也不会导致补跑：

function loop(t) {
  raf = requestAnimationFrame(loop);
  if (!running) return;
  if (!lastT) lastT = t;
  acc += t - lastT;
  lastT = t;
  while (acc >= STEP) { acc -= STEP; step(); }
}

另一个教训是速度。115ms 一格时，第一次玩的人几乎必撞墙；改成 150ms 之后，同样的代码忽然"会玩了"。难度不是数值问题，是节奏问题。快 35 毫秒，体感就是另一个游戏。

生命游戏：把控制权交出去

前两个玩具我都在设计"规则"，第三个我试着什么都不设计——只给网格，让用户自己画。结果它成了我最喜欢的一个：有人在上面画字母，有人画心形，然后一起看它怎么碎掉。

技术上唯一值得说的是环形边界。用取模让上下左右相连，图案就不会在边缘"死气沉沉"地撞墙消散：

const nx = (x + dx + COLS) % COLS;
const ny = (y + dy + ROWS) % ROWS;

玩具教给我的三件事

  1. 手感是能被量化的。"这感觉不太对"通常等价于某个具体数字不对：延迟 35ms、圆角多 4px、缓动曲线选错。玩具让你有耐心把它找出来。
  2. 边界情况会自己找上门。标签页切换、指针离开画布、双击缩放、系统开启"减少动态效果"——这些在正式项目里往往排不上测试用例，在玩具里你一定会撞上。
  3. 做完比做好重要。三个玩具没有一个是"完成品"，但它们都在线、都能玩。这份完整感，比任何设计稿都更让人踏实。
如果你也想动手：从最小的那个开始。一个能让人玩第二次的小东西，比一份完美的方案更有说服力。
