Bento 网格为什么这么耐看

它同时解决了三件事：内容不等量、注意力不均匀，以及作者总想再塞一点。这篇文章讲清楚跨度规则怎么定，以及怎么避免排出空洞。

我第一次被 Bento 布局打动，不是因为好看，而是因为它替我做了决定。传统栅格要求每个区块等宽等高，于是所有内容都被迫长成同一个形状；而真实的内容从来不是等量的——一段自我介绍和一句随机语录，凭什么占一样大的地方？

Bento 的做法是把"重要性"直接编码进面积：越重要的内容，占的格子越多。用户扫一眼就知道该先看哪里，不需要你用加粗、放大、红色来喊。

一、先定列数，再定跨度

我的经验是桌面 12 列、平板 6 列、手机 1 列。12 能被 2、3、4、6 整除，几乎所有常见组合都排得下；6 列是平板的安全值；手机端干脆放弃跨度，回归单列阅读。

关键约束只有一条：每一行的跨度之和必须正好等于列数。否则自动布局会在行尾留下空洞，或者在下一行错位，你就会忍不住加 grid-auto-flow: dense——而那会打乱 DOM 顺序与视觉顺序的对应，键盘用户按 Tab 时会在页面上跳来跳去。

.bento {
  display: grid;
  grid-template-columns: repeat(12, minmax(0, 1fr));
  grid-auto-rows: 100px;
  gap: 18px;
}

.tile--hero    { grid-column: span 6; grid-row: span 3; }
.tile--portrait{ grid-column: span 3; grid-row: span 3; }
.tile--now     { grid-column: span 3; grid-row: span 3; }
/* 6 + 3 + 3 = 12，正好一行 */

注意 minmax(0, 1fr)：写成 1fr 时，内容的最小宽度会把列撑开，一张长图或一行不换行的代码就能让整个网格溢出。加上 minmax(0, …) 才能真正压缩。

二、固定行高，但只在大屏固定

Bento 那种整齐的"硬边"来自统一的行高。但固定行高在窄屏是灾难：内容会溢出卡片，你只能靠 overflow: hidden 把字切掉。

我的处理是移动端让行高自动、大屏才锁死：

.bento { grid-auto-rows: auto; }        /* 手机：内容说了算 */
.tile  { grid-column: 1 / -1; }

@media (min-width: 760px) {
  .bento { grid-auto-rows: 96px; }        /* 平板起锁行高 */
  .tile  { grid-column: span 6; }
}

锁定行高之后要还一笔技术债：逐个体检每张卡片的内容高度。做法很土但有效——把浏览器宽度拖到 1080px 临界点，看哪张卡片的文字被压到贴着下边缘。凡是贴边的，要么减少内容，要么给它多加一行。

三、留白的分配比尺寸更重要

Bento 看起来舒服，一半功劳在间距的一致性。我固定三档：卡片内边距 22px、卡片间距 18px、卡片圆角 24px。比例上圆角略大于内边距，视觉上会更"糯"。

另外一个小细节：卡片内的元素用 margin-top: auto 把页脚推到底部，而不是给每张卡片算高度。这样不同高度的卡片，页脚会在同一条基线上，整片网格立刻显得有秩序。

.tile { display: flex; flex-direction: column; }
.tile__foot { margin-top: auto; }

四、换来的代价

Bento 不是免费的。它有三个真实成本：

  • 内容必须提前想清楚。格子数量固定，意味着你不能"先随便排一下"。这其实是好事，但确实更费脑。
  • 响应式规则会变多。每个断点都要重新分配跨度，我现在是两套断点，再多就该考虑拆页面了。
  • Tab 顺序会被审视。DOM 顺序必须等于视觉阅读顺序，否则键盘用户会迷路——这也是我拒绝 dense 的原因。
顺带说一句：这个站点的首页就是这套规则的产物。你可以把窗口拖宽拖窄，看它是怎么一格一格重排的。

结论

如果你的内容天然不等量、又希望首屏能自己讲清楚主次，Bento 是性价比很高的选择。只要守住三条底线——跨度之和等于列数、大屏才锁行高、DOM 顺序等于视觉顺序——它就很耐看，也很耐用。
